Module 8, Lesson 3: Run repeated test conversions

Run repeated test conversions

The first load almost never works. Repeated test runs let the team find and fix mapping problems before the real go-live load.

Use a non-production environment, or an approved test area kept apart from live work. A well-run conversion usually includes:

  1. a small technical sample;
  2. a representative test conversion;
  3. a corrected full-volume rehearsal;
  4. the final production conversion;
  5. checks after the load, and the move to live work.

Each run uses a controlled mapping version and produces:

  • source counts and checks;
  • extracted counts;
  • loaded, rejected, skipped, and transformed counts;
  • reasons for errors;
  • relationship checks;
  • data-owner validation;
  • defects and corrections;
  • run time and performance;
  • the evidence needed for the next gate.

Do not change mappings during a run without version control. The team must know which rules gave which result.

Rule: Every test run uses one numbered mapping version, so each result traces to its rules.

  • Example A. Cedar Point's second test run uses mapping version 3. Allergy reactions are missing after the load. Because the version is recorded, the team finds the rule in version 3 that dropped them.
  • Example B. At a family medicine clinic, two analysts used different copies of the workbook in one run. No one can tell which rule caused 200 rejected appointments. The team repeats the run under one numbered version.

A result is useful only when the team knows which rules produced it.

Check yourself

  1. Put the five conversion runs in order.
  2. Why must the mapping version stay fixed during a run?
  3. Halfway through a rehearsal, the vendor wants to fix a mapping row while the run is still going. What do you do?

Reconcile and validate with the owners

A clean load report shows that records moved. It does not show that they are right, linked, or usable. Owners must check the data they understand.

Validation asks whether the converted information is complete, accurate, correctly linked, usable, visible to the right roles, and fit for its approved purpose. Reconciliation means comparing numbers from the source and destination and explaining every difference.

Use several methods together:

Method What you do
Count reconciliation Compare source, extracted, loaded, rejected, skipped, and duplicate counts for each group. Explain every difference.
Control totals Compare totals that matter: balances, payments, open items, appointments, documents. A matching total does not prove each record is right. A total that does not match shows a problem.
Field and relationship checks Check values, formats, translations, cut-off text, IDs, documents, and links. Include normal, incomplete, edge, duplicate, and high-risk examples.
Business scenario checks Use converted records in approved workflows. Can staff find the right record, see where it came from, continue an open task, find a document, post a payment, and take the next step?
Access and audit checks Confirm the right roles can see what they need and are blocked from restricted records. Check source, author, date, approval, and audit details.
Client validation Named business owners validate the information they understand. Technical success is not client acceptance.

Set the sampling or full-review rule by risk and clinic policy. Some critical groups may need a full check. Others may use a written sample. The data and domain owners approve the approach. For clinical lists, see the next two sections.

Rule: Explain every count difference, then let the named owners validate what they understand.

  • Example A. A run extracts 21,480 patients. Loaded, rejected, and skipped add up to 21,440. You open a defect for the missing 40 before the validation meeting.
  • Example B. Every appointment loads. When the scheduler opens tomorrow's list, three Lakeshore visits show at Cedar Point main. The counts matched, but the business scenario check failed.

The counts caught one problem. Only an owner using the data caught the other.

Know why clinical lists need clinical validation

Clinicians prescribe, order, and screen from converted medication, allergy, problem, and immunization lists. An error there can reach a patient on the first day.

These lists are not ordinary fields. Drug-allergy and drug-drug checks read them. A list can match every count and still be unsafe. For example, an allergy may arrive as free text that the new system's alert logic cannot read. The prescriber then sees no warning at all.

Clinical validation means qualified clinicians confirm that converted clinical information is correct and safe to use for care. Technical reconciliation cannot do this. It shows that records moved, not that a clinician can rely on them.

Know what can go wrong

Check each clinical list for these common problems:

  • Medications: "active" and "inactive" mean different things in each system; dose, unit, route, or frequency is split or merged; drugs do not match a standard drug code. RxNorm, kept by the National Library of Medicine, gives standard names for clinical drugs.
  • Allergies: free-text substances do not code; reactions and severity are lost; "no known allergies" is confused with "not recorded." These are not the same. A blank list must never convert as "no known allergies."
  • Problems: active and resolved status are mixed up; old diagnoses come forward as active; free-text problems have no code.
  • Immunizations: dates are missing, or vaccine names do not map to a CVX code. CVX (vaccines administered) is the vaccine code set from the Centers for Disease Control and Prevention (CDC). Old doses given elsewhere may also be confused with doses the clinic gave. CVX has codes for vaccines no longer made and for doses recorded without a known product. Use those codes instead of guessing a specific product.

These four lists are data classes in the United States Core Data for Interoperability (USCDI). USCDI is the national standard set of data that health information technology systems exchange.

The Office of the National Coordinator for Health Information Technology (ONC) publishes the SAFER Guides (Safety Assurance Factors for EHR Resilience). An EHR is an electronic health record. ONC's 2025 SAFER Guide on System Management calls for data-migration steps that protect data integrity. This matters most when data moves between EHRs, changes from free text to coded form, or gets new clinical codes.

Rule: A converted clinical list is not safe to use until qualified clinicians validate it.

  • Example A. A patient's allergy to sulfa arrives as free text. The count matches, but the drug-allergy check stays silent when a sulfa drug is ordered.
  • Example B. A patient's old blood thinner was stopped two years ago but converts as "active." The count matches, but a prescriber may think the patient still takes it.

In both cases the data moved correctly by count. Only a clinician could see that it was unsafe.
