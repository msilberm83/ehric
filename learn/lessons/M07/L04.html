Your turn: faded example

If you have done this task on a real project, try this first, then compare with the worked example.

At Cedar Point main, QC tests the referral fax service in build 5.4. When the network is slow, a user who clicks "Send" a second time sends the same referral twice. The specialist's office books two appointments.

  1. Record the defect. The implementer wrote defect D-251: environment test, build 5.4, front-desk role, steps to reproduce, expected one fax, actual two faxes, screenshot attached, linked to interface test IT-14.
  2. Set severity. The implementer rated it High. A required control, duplicate prevention, does not work. The patient is not directly harmed, so it is not Critical under the approved model.
  3. Get the fix. The vendor delivered build 5.5, which disables "Send" while a fax is pending.
  4. Retest. What exactly do you run, with which role, in which build? ____________
  5. Choose the regression set. Name at least three tests you add, and why each one. ____________
  6. Record the evidence. What must the regression record show, including anything you leave out? ____________
  7. Prepare the release decision. Who decides, for what purpose, and what do you hand them? ____________

Field assignment

Use the Cedar Point Internal Medicine practice case (fictional; two locations, Cedar Point main and Lakeshore). Use synthetic data only. Do not use a real client, employer, or patient. Choose one advanced or high-risk workflow:

  1. Complete the specialty or integration-failure training.
  2. Gather the approved requirements, scenarios, build version, roles, risks, and evidence.
  3. Define QC entry and exit criteria.
  4. Write at least eight test cases across relevant test types, including one performance test.
  5. Run or role-play the tests and keep evidence.
  6. Create defects for failed results and assign severity under the approved model.
  7. Correct and retest, then choose, run, and record a risk-based regression set.
  8. Role-play user acceptance with the practice case's authorized client roles.
  9. Match the tested environment and version to the release record.
  10. Make and record the release purpose and decision.
  11. Update the module readiness table.

Knowledge check

  1. Why is technically functional behavior not always an acceptable workflow?
  2. What makes a test case reproducible?
  3. What is the difference between severity and priority?
  4. Why must a fix be retested?
  5. How does a regression test differ from a retest, and which changes should trigger one?
  6. How do you choose a regression set when there is no time to rerun every test?
  7. How can a small team add independence when the builder also performs testing?
  8. What different questions do QC and user acceptance answer?
  9. Why does a pass result belong to a specific environment, build, and release purpose?
