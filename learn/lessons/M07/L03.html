Module 7, Lesson 3: Choose and record a risk-based regression set

Choose and record a risk-based regression set

You rarely have time to rerun every test after every change. A planned set protects the riskiest work first and shows the release owner what was left out.

Choose the set

  1. Start from the change record. Write down what changed, in which build, and why.
  2. Trace what it touches. Use your QC plan's links from requirements to configuration, roles, queues, interfaces, and reports.
  3. Add the neighbors. Include tests that share a part with the change, such as the same role, template, rule, or code table.
  4. Keep a core set. The core set is a short, approved list of the highest-risk workflows. Examples are patient identification, results routing, medication and allergy display, sensitive-record access, and claim creation. Run it after every build or upgrade.
  5. Rank by risk. Weigh how likely the change is to affect a workflow against the harm if it breaks. Safety, privacy, data, and money come first.
  6. Record what you left out. List the tests you chose not to rerun and why.

You own the proposed regression set. It is your professional work. You do not need permission to run more regression tests. The QC lead agrees on the set. Specialist owners, such as privacy or clinical leads, confirm tests in their areas. The release owner is the named client or project person who approves a version for its next stage. The release owner accepts any risk from tests not rerun.

When a defect is found, add a test for it to the regression set. Then the same failure cannot quietly return in a later build.

### Keep the evidence

A regression record shows:

  • the change or build ID and what changed;
  • the regression set, with the reason each test was chosen;
  • environment, build, tester, and date for each rerun;
  • the new result beside the earlier passing result;
  • any new defects, linked to the change that caused them;
  • tests not rerun, the reason, and who accepted that risk.

Keep earlier test cases and results. Without them, you have nothing to compare. The FDA guidance notes that checking a system again after a change is much harder without them.

Short example

At Cedar Point, a fix corrects Lakeshore lab results that were going to the wrong provider. The retest passes. The implementer's regression set adds main-location routing, covering-provider routing, abnormal-result flags, the nurse result inbox, and the lab interface acknowledgment. The covering-provider test now fails. The implementer opens a new High defect and links it to the fix. The module stays unreleased until the test passes.

Rule: You choose the regression set; the release owner accepts what you left out.

Protect QC independence

People who built a feature tend to test what they meant to build, not what they built. Independent review catches what the builder cannot see.

QC needs enough independence to challenge the result. That does not always mean a separate department, especially in a small organization. It does mean a reviewer who is not relying only on memory of the build. The reviewer must also be able to report findings without pressure to protect the schedule.

When the same person must build and test, add controls:

  • peer review;
  • approved test scripts;
  • recorded evidence;
  • client user acceptance;
  • specialist approval for controlled areas;
  • a release decision by someone other than the builder.

The project plan should name who does configuration testing, independent QC, user acceptance, security review, and final release. Each answers a different question.

Rule: When the builder also tests, add controls and give the release decision to someone else.

  • Example A. Cedar Point has one configuration analyst. She builds and tests the Lakeshore check-in forms. A second analyst reviews her scripts and evidence, and the project manager makes the release decision.
  • Example B. A vendor builder tests his own lab-order set. The clinic's nurse lead runs the approved scenarios, and the clinical lead approves release.

Neither project had a QC department. Both still had a second reviewer and a separate release decision.

  2. Why is a separate QC department not always required?

Run QC after every module

If QC waits until the end, defects get buried under later work and become harder to find. Testing after each module keeps problems small.

This course places QC after each module. Use a repeating cycle:

build → builder check → QC → correct → retest and regression → approve → train or release

Training may reveal a new requirement or defect. Send it back through the cycle. Do not let training become the first planned test. Do not assume a passed configuration stays valid after later changes.

Keep a module readiness table:
Module / workflow Approved requirement version Build version QC status Training status Open Critical / High defects Accountable release owner Release state

This table becomes a main input to go-live readiness in Module 11.

Rule: Every module goes through the full QC cycle before it is trained or released.

  1. Put the seven stages of the QC cycle in order.
  2. Why is training a poor place for the first planned test?
  3. A defect found in training is fixed. Where does it go next in the cycle?

Keep user acceptance separate from QC

QC and user acceptance answer different questions. If you merge them, a client user may approve something only a privacy or safety owner can approve.

QC checks requirements, risks, and expected behavior through planned tests. User acceptance testing (UAT) is when authorized client users confirm they can use the built workflow to do the approved work.

Both matter. QC should not approve business policy for the client. A client user should not waive a security or safety control they have no authority to waive.

Use the acceptance scenarios from discovery. Record the scenario, participant, environment, expected result, actual result, findings, and approval. A general "UAT passed" email is weak evidence, because no one can see what was tested.

> **Rule:** A user can accept a workflow but cannot waive a control they do not own.
  • Example A. In UAT, the front-desk lead finds that schedulers can see behavioral-health visit reasons. She says it is fine. You record the finding and send the access question to the privacy officer.
  • Example B. In UAT, the billing lead wants a claim edit turned off to save time. You record the request and send it to the billing compliance owner.

Both users were real client representatives. Neither owned the control they wanted to change.

Check yourself

  1. What question does QC answer, and what question does UAT answer?
  2. Why is a "UAT passed" email weak evidence?
  3. A nurse in UAT accepts a workflow that lets her see psychotherapy notes. What do you do?

Record the release decision

A tested version is not ready until someone with authority approves it for a named next stage. Without a recorded decision, nobody knows which version training or go-live is using.

A release decision approves one identified version for one purpose: training, UAT, rehearsal, or production. The release owner makes it, using the evidence from QC, regression, and UAT. You prepare the record. It shows:

  • the version and environment;
  • the release purpose;
  • exit criteria met or not met;
  • open Critical and High defects, each with its recorded decision;
  • tests not rerun and who accepted that risk;
  • accepted limits and who approved them;
  • the decision, the decider, and the date.

Then update the module readiness table.

Rule: Each tested version needs a recorded release decision for a named purpose.

Check yourself

  1. What does a release decision approve?
  2. Why must the record name a release purpose and not just "approved"?

Worked example: a pending eligibility check

Cedar Point's advanced front-desk training includes an insurance eligibility check. An eligibility check is a request to the payer asking whether a patient's coverage is active. Here is how the implementer handled a failure found in training.

  1. Ran the failure scenario, not just the normal one. Staff sent a synthetic eligibility request. The normal response appeared correctly. In the delayed-response scenario, the request stayed "pending." The queue did not show how long it had waited, and no one was assigned to watch it. Produced: a training observation in the open-item register. Why: the failure path is part of the workflow, so it must be practiced.
  2. Sorted the finding. The implementer saw that no requirement said who watches pending checks. That made it a missing requirement, not a training question or coaching need. Produced: a new-requirement entry with the billing owner named. Why: more training cannot fix a rule that does not exist.
  3. Sent the decision to its owner. The client billing owner approved a rule: any check pending over 30 minutes goes to the billing lead's queue with an alert. Produced: an approved requirement, version 1.1. Why: the client owns business policy; the implementer does not invent it.

Why do you think the implementer sent this to the billing owner instead of writing the 30-minute rule herself?

  1. Built the change under control. The builder added the queue view and alert in build 6.2. Produced: an updated build and promotion record. Why: QC results apply only to an identified version.
  2. Tested against the new requirement. QC tested success, rejection, delayed response, duplicate prevention, access, and acknowledgment. Produced: six test cases with results and evidence. Why: each test type covers a different way the workflow can fail.

Why did QC test duplicate prevention when the problem was a pending response?

  1. Ran a regression set. The implementer reran the core set and the claim-submission tests that share the billing queue. All passed. Produced: a regression record with earlier results attached. Why: the new queue and alert could affect other billing work.
  2. Updated training and released. The job aid and the training scenario were updated. The release owner approved build 6.2 for training. Produced: a release decision record and an updated readiness table. Why: exit criteria require training materials to match changed behavior.
