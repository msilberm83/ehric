Module 7 — Start here: outline and the problem

Chapter outline

This chapter takes one tested version of the build from quality control (QC) to release. Steps 2 and 3 finish training work carried from Module 6. Steps 4 to 12 are the build, test, and release path. The steps follow the order taught.

  1. Define what quality means. For each workflow, decide which meaning of "it works" the requirement demands. You produce a clear quality target.
  2. Finish advanced and specialty workflows (carried from Module 6). Use the Module 4–6 method for specialties, devices, and interfaces. You produce specialty training evidence.
  3. Train the failure path (carried from Module 6). Teach users what a delayed, rejected, or failed interface looks like and what to do. You produce integration-failure and downtime training.
  4. Control the build QC receives. Confirm the environment, version, contents, and release purpose before testing. You produce a build and promotion record.
  5. Build the QC plan from requirements. Trace every test to a requirement, risk, or control, and set entry and exit criteria. You produce the QC plan.
  6. Design reproducible test cases. Cover functional, workflow, access, data, interface, form, reporting, performance, accessibility, and downtime tests. You produce test cases and results.
  7. Record defects by impact. Assign severity from the agreed model and link each defect to its test. You produce defect records.
  8. Retest and run regression tests. Confirm each fix, then choose and run a risk-based regression set after every change. You produce retest and regression records.
  9. Protect QC independence. Add peer review and a separate release decision when the builder also tests. You produce a named review plan.
  10. Run QC after every module. Repeat the build, check, test, correct, retest, and approve cycle. You produce a module readiness table.
  11. Record user acceptance. Authorized client users run the approved scenarios. You produce acceptance evidence.
  12. Make the release decision. The named release owner approves each tested version for its next stage. You produce a release decision record.

You will produce:

  • specialty and failure-path training evidence;
  • a build and promotion record for each tested version;
  • a requirements-based QC plan with entry and exit criteria;
  • test cases, defect records, retest records, and regression records;
  • user-acceptance evidence and a release decision for each tested version;
  • an updated module readiness table.

Checked off when: every trained module has a tested, identified version, a recorded release state, and no Critical or High defect left open without a decision by the proper authority.

The problem

Cedar Point Internal Medicine has two locations, Cedar Point main and Lakeshore. In QC, lab results for Lakeshore patients went to the wrong provider. The vendor sends a new build on Thursday. Staff training on the results module starts Monday.

The builder tells you, "It's fixed. You can close the defect." You run the failed step again. The Lakeshore result now reaches the right provider. The QC lead wants to close the defect today so training can start.

Before you read on: Is one passing step enough to close this defect? If not, what else must you check, and who decides which tests to run?
